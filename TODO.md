## Pre-Release Priorities (Blocking)

- [x] Unified semaphore/concurrency redesign -- replaced the memory-derived, per-directory-level concurrency calculation with a fixed, tiered pool hierarchy, built from real production log evidence rather than guesswork
  - **Pool 3** (transfers, hashing, MOVE/MKCOL/DELETE -- "everything else"): the existing `content_semaphore`, fixed at 6 permits matching Nextcloud's own desktop client default (`OWNCLOUD_MAX_PARALLEL`), never a memory-derived number. Checks only its own occupancy, never a combined total across the other pools -- a deliberate choice over the alternative (Pool 3 itself checking a global running total before handing out permits): the two behave identically when nothing's contended, differ only under genuine, all-pools-saturated conditions, not worth the real added complexity for a difference that narrow in practice
  - **Pool 1** (discovery -- `list_remote_with_recovery`, the calls that actually drive the recursive walk) and **Pool 2** (confirm/detect -- the ETag root-check, standalone rename-confirmation stats) each get a small, dedicated 2-permit reserve via a new `HybridPool`: tries Pool 3 first (non-blocking), only falls back to its own reserve if Pool 3 is genuinely full right now. Guarantees these can keep making progress -- "keeping up with reality" (what still needs attention) matters more than "acting on it promptly" -- even while Pool 3 is fully saturated with large transfers
  - **Pool 0** (conflict resolutions): confirmed already correctly, structurally isolated -- never touches Pool 3 or either reserve at all, so a resolution the user is actively waiting on never queues behind background work
  - Root cause confirmed via real [debug] log analysis, not assumed: a single ~6.2GB file (`backup.json`) was found holding one Pool 3 lane for 7+ minutes with 5 other lanes sitting completely idle, since nothing else remained in the tree to fill them by that point in the round -- the semaphore mechanism itself was working correctly, there was simply no other parallel work left to hand idle lanes to
  - `Semaphore::try_acquire()` added (non-blocking variant) specifically to support `HybridPool`'s own "try shared, fall back to reserve" pattern
  - Files: `sync.rs`, `main.rs`

- [x] Chunked content-hash comparison for large files -- files at or above ~512 MiB (4 chunks' worth) get split into 128 MiB chunks, hashed independently, and compared as results come back, rather than reading the entire file on both sides before any comparison can happen at all
  - Each chunk acquires its own Pool 3 permit (still respects the global budget), capped at 4 concurrent chunks per file -- a deliberate compromise: letting one huge file claim all of Pool 3 finishes that one file fastest but blocks every other, unrelated piece of Pool 3 work for its entire duration (reproducing the exact "processed_count stalls, then bursts" symptom this investigation started from); capping at 1 removes that risk but gives up all the concurrency benefit. 4 leaves headroom for other work in the common, mid-round case while still giving a huge file real, multi-way parallelism
  - Stops submitting new chunks the moment any chunk reveals a mismatch, a read failure, or the server not honoring the `Range` request -- but chunks already in flight at that instant are allowed to finish naturally and their results discarded, rather than forcibly cancelled (a streaming hash mid-read on its own OS thread can't be safely aborted once started)
  - `webdav::hash_content_range` added, returning a `RangeHashOutcome` distinguishing a real chunk hash (206) from the server ignoring the `Range` header entirely (200, silently returning the whole file) -- the latter falls back to the existing whole-file hash path for that file, not treated as a valid chunk result
  - Confirmed working against real production data: the same file that previously held a lane for 7+ minutes completed in ~31 seconds once chunked, visible directly in [debug] output as ~9 rapid acquire/release cycles at "4 now in use" rather than one long-held permit
  - Files: `webdav.rs`, `sync.rs`

- [x] SHA256 -> XXH3 for all content-comparison hashing (not the chunked-upload folder-naming hash in `upload_via_chunking`, which stays SHA256 -- different purpose, small input, no performance concern there). Not a security boundary, so a fast, non-cryptographic hash is the right tool; confirmed several times faster than SHA256 on the same input via independent benchmarking elsewhere in the ecosystem

- [x] Local rename/move detection -- v1 treated a rename as delete+create. Design changed substantially through discussion before landing; final version is simpler than what was first scoped, not more
  - **Live GFileMonitor pairing (originally "Case A") was dropped entirely, on purpose.** Checked the real Nextcloud desktop client's own Linux inotify handler: it does zero cookie-based move pairing -- every event, `IN_MOVED_FROM`/`IN_MOVED_TO` included, collapses into one generic "something changed here" signal, with all actual rename detection happening at the next discovery scan. Matches the real Nextcloud client's own reasoning exactly: its move-check explicitly skips size/mtime corroboration for directories ("Directories and virtual files don't need size/mtime equality"), trusting the inode match alone -- adopted verbatim here (`sync_child_directory`'s pairing check has no secondary check; `sync_child_file`'s does, files still need it since an inode match alone only proves "same file," not "content unchanged since last sync"). Exact-string exclusion rules have no attachment to a folder's actual identity, so they go silently stale on any rename along their path: not just the excluded folder itself being renamed, but any ancestor directory renaming too (`/This/That/TheOther` -> `/This/ThatOne/TheOther`), and not just a rename in place but a move to a new parent entirely (`/This/That/TheOther` -> `/This/That/Those/TheOther`). One mechanism should cover all three: whenever a directory rename/move is detected, check whether any exclusion rule's stored path has the *old* path as a prefix (a full match counts too -- the excluded folder itself moving is just the case where the whole rule is the matched prefix) and rewrite that prefix portion, leaving whatever comes after untouched

- [x] Per-file "don't touch anything modified too recently" filter
  - `MIN_FILE_AGE_SECS` (5s) gates `SyncAction::Upload` specifically in `sync_child_file` -- the only action that reads and transmits a local file's live byte content, so the only one actually at risk from a concurrent mid-write. `Download`/`DeleteLocal` don't need the same gate: `decide_action` only returns those when local is confirmed unchanged since the last successful sync, so a recent local mtime there just reflects a recent prior sync, not an in-progress write -- gating those too would incorrectly stall legitimate downloads
  - Skipped silently (not logged, not marked skipped) -- self-resolving within a few seconds on the next round, not actionable or surprising the way `Excluded`/`SkippedTooLarge` are
  - Still relevant to rename detection whenever that lands: hashing/pairing a file mid-write risks a wrong pairing decision, and this is now the precondition that makes that safe
  - Files: `sync.rs`

- [x] Permission/executable-bit preservation -- narrower than the name suggests, deliberately. Local-to-local, one direction only, not general chmod sync
  - What's real: `local_mode`/`download_with_mode` in `sync.rs` capture a file's existing local permission bits before an overwrite (`SyncAction::Download`, `resolve_keep_remote`, `resolve_keep_both_rename_local`) and reapply them after, so a re-download no longer silently resets e.g. an executable script's `+x` bit to the OS/umask default
  - What's structurally impossible, not just unbuilt: WebDAV has no protocol-level channel for POSIX mode bits at all -- confirmed by checking whether Nextcloud's own `oc:permissions` WebDAV property covers this (it doesn't; that's their internal sharing/ACL model -- read/write/share/delete capabilities -- a completely different concept from `rwxrwxrwx`). Also confirmed the *official* Nextcloud desktop client has the identical limitation: [nextcloud/server#6725](https://github.com/nextcloud/server/issues/6725), open since 2017 and tagged `enhancement` (not `bug`), shows `chmod +x` on one machine arriving as `-rw-r--r--` on another after a real sync. So a brand-new file, or one that needs its permission *propagated* to another device, just gets default permissions -- there's no wire format to carry that intent, on this client or any WebDAV client
  - Chmod-restore failure is best-effort (doesn't fail the whole sync action) but is logged, not silently swallowed -- see `SyncEvent::PermissionRestoreFailed`
  - Files: `sync.rs`, `status.rs`

  - `expires_in <= 0` (no known expiry) -> recheck hourly instead of not checking at all, in case the account's situation changes later
  - Files: `goa.rs`, `main.rs`

## Known limitations (by design, not oversights)

- Local watch debounce (2s poll, 3s settle, `main.rs`) and the post-round watch rebuild (`watch.rs`) are fixed constants, not configurable
  - Rebuilding the whole watch set after every round (vs. incrementally off `sync.rs`'s own create/delete calls) is simplicity over efficiency -- fine at the tree sizes targeted, revisit only if it isn't
- Battery-aware polling not implemented -- `remote_poll_interval_minutes` is a flat number regardless of battery state.
- Chunked upload exists (`upload_via_chunking` in `sync.rs`, Nextcloud's own proprietary chunking API -- MKCOL/numbered PUT/MOVE), gated behind confirmed ETag capability (`chunking_base_url`) -- this replaced an earlier version of this note claiming chunking wasn't leverageable at all, written when the app still mounted through GVfs; the direct WebDAV client has no such restriction. What's still genuinely missing is *resuming* an interrupted chunked upload after a restart, not chunking itself -- a narrower gap than "no chunking," and not yet scoped in detail
- Single account active at a time, by explicit choice ("for simplicity") -- other accounts' folder configs are preserved (not deleted) if you switch away, but only the active account syncs or shows folder detail
